# Prompt lookup priority: source-only decision

Current immutable2362/source4fcb: useful proposal hypothesis, not yet a demonstrated speed opportunity. No source change, build, inference or new capture. Exact copied file SHA256s are in source-identity.json.

1. Target verification remains mandatory. `program_impl.h:2243–2270` fills the ordinary MTP ingress from `sequence.mtp_drafts`; the proposal source is not encoded in the verifier. `mtp_impl.h:120–145` always calls `target_verify_accept`, which invokes the normal target forward/replay record and `speculative_accept_greedy_drafts`. In `speculative_round.cuh:121–143`, temperature<=0 accepts only the longest draft prefix exactly equal to target argmax, then emits the target divergence/bonus token. A long N5 continuation can therefore replace MTP proposals without changing the request sampling policy or skipping target verification. This is an algorithmic observation, not a new end-to-end bit-equivalence qualification.

2. Current lookup is a fallback only (`program_impl.h:1061` after commit and `2243` before ingress): it runs when mtp_draft_count==0. `prompt_lookup.h` tries N5→N4→N3→N2 and does not expose which matched. A priority-N5 experiment must distinguish N5, not relabel every result as N5. Result storage is exactly5tokens, while max_drafts has no clamp to5: passing a larger CLI window can overrun it. Keep K3 and clamp any future helper to min(configuredK, tokens.size()); no draft-window enlargement is proposed.

3. There is NO existing verify-only or no-next-draft MTP Graph. `mtp_impl.h:147–179` always performs next-round preparation, MTP alignment, selected hidden, one proposal head, then K−1 serial AR forwards/heads. For K3 this is alignment +3heads +2AR. Masked current_extents/next_extents do not remove those dense nodes. `program_impl.h:1590–1617` captures one MTP family for eachB/envelope, and2223–2227 installs it by B/frontier. Merely replacing drafts on CPU changes acceptance possibilities; it does not remove GPU draft work.

4. Shortest future implementation with actual work reduction: add a distinct `build_next_proposals` capture mode/family (include mode in graph selection/topology; no runtime mutation of a captured bool). Keep target verify and MTP alignment, omit only `mtp_propose_batch` and the K−1 AR loop when the mode is false. Explicitly zero next_extents before egress; never read stale next_drafts on host. Alignment must remain because decode-entry requires mtp_kv_valid==execution_frontier (`program_impl.h:2208`), and commit currently advances that field to the accepted frontier (`1051`). Simply omitting alignment while advancing this field would lie about backend KV. Truly target-only execution requires a separate lazy backend-frontier catchup design and is not the minimal option.

5. To keep the first mechanism bounded, a no-next-draft family would only be selected for a whole batch whose current rows all have a strong N5 continuation; mixed batches retain the full MTP graph. Next-round N5 hits are unknown until target results commit. A subsequent miss must safely fall back with zero current extent/full graph to rebuild proposals, which can lose an entire multi-token round. Alternatively splitting hit/nonhit rows duplicates target weight reads; it is not assumed beneficial. Original target T=B*(K+1), replay geometry, partial commits, terminal cancellation and GDN deferred controls remain unchanged. Required tests cover full→lookup→miss→full, partial accept/commit0..4, slot15/31, row permutation, stale proposal clearing and graph replay/state equivalence.

6. Offline evidence gap: delivered original2362 client16/native16 and newclient16/native12 archives contain actual prompt IDs and complete client/native counts/timings, but no generated IDs or response text. AIPerf export contains only metadata/metrics; request_done contains result lengths and speculative aggregates. Neither near-perfect MTP acceptance nor random input IDs establish N5 continuation coverage. No synthetic response/re-encoding is substituted. Before implementation, need actual historical generated IDs or a separately authorized bounded output-observed diagnostic; then causally build each ledger from prompt+past generated tokens, score N5 proposals against future output only as an offline target, and measure all-rows hit streaks and misses. Such offline coverage would still not establish GPU speed.

Decision: do not implement solely on existing aggregate acceptance. The clean minimal path is N5-specific CPU proposal selection plus an independent **verify+alignment, no-next-proposal** graph, contingent on actual repeated-output coverage. It can save heads/AR, not target verify/alignment or prefill, and cannot by itself promise overall3–4x.
