# 单卡 NInfer/MTP 可移植部署与性能验证计划

**Goal:** 两台机器完成相同、可复现的 NInfer/MTP 环境；仅第一台执行基准与性能边界实验，第二台完成部署和短功能检查以备后续并行验证。

**依据：** 根目录两份评分 MD、原版 eval.zip、submission/PROTOCOL.md 及既有 NInfer/MTP 调优证据。用户已授权部署、适配、评测与汇总，开发仍落 main。

**命名与适用范围：** NInfer 推理与评测工具按功能命名，数据前缀、CUDA 路径、构建并行度和下载源可配置；机器名仅用于节点清单、实测结果归属与运维连接。下列 UCloud 节点是本轮实例，不是方案名称或对其他机器性能的保证。

**机器分工：** ucloud1 使用现有 SSH 别名 `ucloud`；ucloud2 使用 `ucloud2`。两台均为单张 49,140 MiB RTX 4090、驱动 610.57.04、约 90 GiB 内存。工作目录选可写且空闲约 491GB 的 `/workspace/InferX`；该目录当前属于容器 overlay，不能承诺实例释放后持久化。关键源码、配置、结果及时回传本地仓库。

**方法：** 先复用固定 v2 权重和 SM89 源码，构建一次后向同发行版第二台分发；模型通过 hf-mirror 获取并核对 SHA256。与官方 API 不兼容处只做保持原义的适配，原版评测工具不修改。构建/缓存/临时文件均位于工作目录，不改驱动、功率或全局 Python。

## 执行步骤

- [x] 两机盘点：OS、CPU affinity、GPU、工具、磁盘、已有进程、模型与 tokenizer 来源；保存原始记录。
- [x] 准备隔离工具链、固定 NInfer/xgrammar 源码与模型；对缺失编译依赖做隔离安装，记录来源与版本。
- [x] 在第一台编译；验证 `/models`、chat、流式 completions、token-ID prompt、ignore_eos、usage、缓存隔离。适配必须先有失败探针/测试再修复，不得伪造 token 或缓存语义。
- [x] 相同构建与模型准备到第二台，核对环境和哈希、短请求/工具调用/重启检查；不重复压测。
- [x] 第一台分阶段调参：MTP0/4/7，活动请求数与 prefill chunk，必要时 KV 精度/上下文。先小规模筛选，留存失败、截断、接收率和显存，不穷举无关组合。
- [ ] 以选定配置运行原版 C1/C2/C4/C8，每档100、预热8、输出512；优先严格模型8192输入，按 PROTOCOL.md 单列任何口径差异。配套1秒 GPU采样、服务日志和环境锁。
- [ ] 第一台运行原版 IFBench前100、batch2、只显式覆盖max_tokens32768；记录展开配置、四项分数及循环/截断/协议失败。长文本、逻辑、代码功能另列，不能替代 IFBench。
- [ ] 汇总吞吐极值、同时满足 TTFT/TPOT SLO 的配置、质量和失败边界；区分实测上界与理论上限、支持的推断与待验证原因。
- [ ] 两台保留可用服务和身份可核验的启动/停止命令；更新 submission 的报告、配置、TODO 和源码快照，验证后正常提交/同步 main。

## 验收与记录

正式负载与研究探针分目录；不把 warm prefix、短提示 decode 或同时使用两张 GPU 的总和当比赛成绩。保存原版 runner 和输入哈希、最终源码补丁及构建哈希、权重/词表哈希、逐请求输出、错误、GPU采样、两机服务状态。安装依赖和长期实验通过有日志/退出码的独立进程运行；只终止本轮创建且身份匹配的进程。
