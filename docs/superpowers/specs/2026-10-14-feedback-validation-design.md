# 单卡代码生成与验证：瓶颈证伪实验

## 意图与授权

用户要求先验证研究假设，安装 brainstorming、writing-plans，制定计划并到 vlm-server 实测；已明确继续执行。下载必须经过 hf-mirror，并放在 HDD 数据盘。用户允许使用两张 RTX 4090，竞赛约束仍是每个实验单卡。无需绑定 GPU/DRAM/SSD 三级架构。

待检验假设：代码 Agent 的生成与 CPU 验证互相影响，实际成本随并发和反馈变化；在异步验证、成功即取消和固定并发充分调优后，仍有显著、稳定的资源调度空间。首轮只验证候选生成—执行测试循环，不将其外推为完整仓库 Agent 或修复流程。

## 作者选择与实验边界

2026-10-14 最终模型修订：用户明确要求较大的 Qwen3.8 dense 模型，已核对为 **Qwen3.8-27B**（模型页面总参数标签约 28B）。主配置为 `unsloth/Qwen3.8-27B-GGUF` 的 `Qwen3.8-27B-UD-Q4_K_M.gguf`，文件 16,464,440,224 字节，revision `4ca720788d1e01f1bff70c033e0d0028fd02e502`，LFS SHA256 `322e194ff79741c7baa497c240f677f54b201b0efab44ca8e50f122b39123482`。后端为 llama.cpp v0.6.0，CUDA 12.6、SM89、本机回环 HTTP；保留同一调度器和验证器。3B、14B 和 Qwen3.5 的准备均未产生 GPU 评估数据，已停止相关下载，不作为主实验结果。

新配置先验证并发槽位 8、每槽位 2048 token、全部模型层 GPU offload，记录 KV/recurrent state 实际显存；不足时降低上下文/最大并发并记录，不偷偷 CPU offload。关闭 thinking 以避免将 768 token 上限全消耗在推理过程；用服务端 chat template 构建一致提示。流式候选取消通过关闭 HTTP 响应触发，须实测服务端槽位归还。请求之间缓存策略相同，记录冷/热提示的限制。模型与源码仍全放 HDD，经 hf-mirror 获取模型并校验发布哈希。下载使用 hf_transfer 0.1.9 的 64 个并行 range，避免原 aria2 16 连接约 1 MiB/s 的传输瓶颈。

Dense 表示非 MoE，不代表纯全注意力：该模型 64 层采用 16 × (3 Gated DeltaNet + 1 Gated Attention)。服务内存包括 attention KV 和 recurrent state。按官方结构及 f16 KV 估算，attention KV 每 token 为 16 × 2 × 4 × 256 × 2 = 65,536 字节；16384 token 总池约 1 GiB，尚未计 recurrent state、权重和工作区。此处仅为容量预估，不能替代启动日志和 nvidia-smi 实测。本轮仅用文本能力，不加载视觉 projector。

- 数据：公开 HumanEval 全集下载后，按固定 seed=20261014 打乱；16 题调试/选择并发，48 题评估，其余留作后续扩展。题目选择不依赖模型输出或正确性。使用原始测试作为执行验证器，测试代码和 canonical_solution 不进入生成提示。
- 每题最多 8 个候选；temperature=0.8、top_p=0.95、max_tokens=768；同一题和候选序号的 seed 在策略间相同。并发和取消可能导致引擎非确定性，记录真实生成结果，不声称严格配对输出。
- 固定并发基线宽度 1、2、4、8，宽度只限制活跃的生成请求。生成完成即排队异步验证，并立即补充生成，不等待验证失败；宽度 1 也保留生成与验证重叠。一旦通过即取消该题其他生成/验证；直到预算或 120 秒期限。调试集选出质量优先、其次平均截止时间截断的解决耗时最小的宽度，在评估集锁定。
- 固定使用 tokenizer 的 chat template；user 提示要求实现给定 HumanEval 函数规格，返回包含 imports 的完整 Python 模块，不给出测试或参考答案。提取首个 python/无语言 Markdown fenced block；没有 fenced block 就将完整响应当源码；语法错误计失败，不追加 canonical_solution、不做因策略不同而不同的修复。
- 单题循环依次运行，以分解候选级竞争；本轮不模拟多租户到达。验证进程数默认 2，固定 CPU affinity；记录进程启动成本与测试执行成本。除非真实测到验证压力，不通过 sleep 或重复放大测试伪造瓶颈。
- 两轮不同采样 seed；评估顺序交错/随机化，记录热身、GPU 温度、显存与系统负载。GPU 0 主实验，GPU 1 可独立复验，不能合并计算资源。引擎使用 8 个逻辑 CPU，验证使用另外 2 个 CPU，避免这台 112 线程服务器掩盖竞争；记录其约 503 GiB 内存，不能冒充普通桌面配置。

## 工程和安全要求

全部下载、环境、缓存、临时文件和原始实验数据位于 `/home/guokc/mypro/gnn-mount-sda1/InferX/`。先验证该路径位于 `/dev/sda1` 的 HDD 挂载，再写入；本地仅保存源码、计划、轻量证据和报告。设置 HF_ENDPOINT=https://hf-mirror.com，固定并记录数据与模型版本和文件哈希。不得使用或写入全局 HF 缓存。

不改驱动、不改其他 conda 环境、不终止他人进程、不清系统缓存。生成代码不得直接在用户宿主权限下自由运行。服务器 bubblewrap 的 namespace 权限不可用；验证采用无额外文件描述符、无秘密环境变量、CPU/地址空间/输出大小限制的独立 Python 进程，预加载常用标准库后装载不可撤销的 seccomp allowlist，禁止文件打开、网络、fork/exec 等系统调用。过滤器安装失败则拒绝执行；先用已知正确/错误/死循环/文件访问/网络访问样例测试。模型输出被视为代码基准中的普通非对抗性程序，此沙箱不是通用恶意代码托管服务。

## 组件与记录

环境脚本负责 HDD 路径和依赖；下载脚本负责固定 revision 和数据 manifest；沙箱负责隔离与验证结果；异步调度器负责有界并发、预算、绝对截止时间和取消；llama.cpp HTTP 适配器负责流式 token 计数、断连取消和服务端空闲确认；分析器只读 JSONL，产生可复核汇总。

每次候选记录：题号、候选号、seed、策略、提交/首 token/生成结束/验证入队/验证开始/结束/取消时间、完成 token 数、验证结果、源码哈希与可追溯输出。时间使用单调时钟，带相对起点。每题记录 solved、首次通过时刻、总 wall time、停止原因、有效与被取消候选的已观察 token；无法获知服务端尾部已算 token 时明确计数为下界。

每策略报告成功数、deadline 内成功率、成功题延迟和失败按 120 秒计入的截断耗时、GPU 吞吐、验证排队/执行占比、成功前已生成但未采用的 token、取消耗时和 timeout。禁止只展示成功题加速比造成幸存者偏差。

## 判断和后续分支

优先证伪：成功题的验证反馈占比定义为 `(获胜候选验证结束 - 该候选生成结束) / 首次通过耗时`，包含排队、进程启动和测试；按题求中位数、p95，并分别报告两轮。不能把所有候选验证耗时求和除以 wall time 来冒充关键路径占比。另报验证槽位的 busy-time/(workers*wall-time)、候选队列等待分位数，以及未解决题的最后生成完成到最后验证结束的尾部耗时（截断为非负）。

在开发集选定的基线下，若上述成功题反馈占比中位数两轮均低于 5%，且 p95 低于 10%、验证排队 p95 低于 0.1 秒，则当前 workload 不支持以验证反压为主的研究动机。报告观察到的不足，不实现无证据支撑的复杂调度器。若成功题太少（任一轮不足 12）则结论为证据不足。

若成功题反馈占比中位数两轮均 ≥10%，再加最小队列反压策略：待验证量超过 worker 数时暂停新候选，验证反馈到达即恢复；与所有固定宽度比较，质量保持的前提下关注 ≥20% 延迟改善。这些百分比只是作者的选题筛查线，不是统计显著性或会议录用标准。中间区域报告不确定。

完整论文仍需更难的仓库级真实测试、多个模型/引擎/上下文长度、CPU 配额与负载扫描、多租户轨迹、公开开发测试和独立最终测试、修复预算策略、置信区间及最新相关工作对照。本轮允许结论为否定或证据不足。
