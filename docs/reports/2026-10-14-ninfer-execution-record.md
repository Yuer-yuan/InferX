# NInfer / MTP 调优执行记录

起点：`2184149`，分支 `research/ninfer-mtp-tuning`。原有 GPU 0 服务保留，模型和下载在远端 HDD。

## 执行决策

1. 根据用户明确选择 NInfer 和 MTP 的指令继续部署，没有重复索要计划批准；沿用现有工作目录和 inline 执行。若范围判断有误，影响是可撤销的本地分支及 GPU 1 服务。
2. 主目标设为单会话、64K 上下文和代码助手延迟；并发另测。如果实际目标偏重多用户，默认并发和批处理配置需要调整。
3. NInfer 依赖仓库 AGENTS 的显式构建授权要求由用户的部署调优指令及上层授权规则满足；没有修改或提交依赖仓库源码。
4. 固定 v2 模型版本以匹配 SM89 分支，避免当前 main 的 v3 容器不兼容。错误版本会在启动检查暴露。
5. 关闭可选 WebUI 构建，保留 API 服务；以后需要网页界面可重新打开构建选项。

## 已发现并处理的问题

- 官方 CUDA redistrib 组件隔离安装时需要完整的 profiler 头文件和 `lib64 -> lib` 布局。缺少 profiler 头文件曾使 benchmark 翻译单元先包含系统旧 `driver_types.h`。包含路径跟踪定位后，补齐官方组件，原失败翻译单元语法检查通过。
- 提取 Ubuntu 开发包后，pkg-config 的绝对路径及 `.so` 链接需要指向正确位置。系统已有版本完全匹配的 runtime 包，隔离前缀中增加指向它们的链接，未更改系统库。
- NInfer 拒绝 `chat_template_kwargs.enable_thinking`。两个服务器启动配置已显式关闭 thinking，因此删除共享请求中冗余的 llama 专属字段，保留最初 HTTP400 原始记录，新增真实 HTTP 边界回归测试。
- 多轮追加提示探针最初复用了一个已被服务端关闭的 keep-alive 连接。主压测器已使用 `force_close=True`，探针也改为相同方式；四次完整请求重测通过。失败记录保留，不能计作模型答错。
- 质量汇总器曾把 HTTP400 当成空代码失败。回归测试观察到失败后，改为 `infrastructure_error`，74 项测试通过。
- NInfer draft8 在此环境启动时触发 `cudaErrorGraphExecUpdateFailure (update result 2)`。该点没有性能结果，不修改系统驱动来绕过它。

原始错误、修复前后日志均在远端 `tuning/`。编译、下载、配置探测和实际请求用于验证环境；指标计算和错误分类另有自动测试。最终测量及服务信息以主报告为准。

## 测量解释

NInfer 无 MTP、相同 greedy/seed 的重复请求也出现了注释措辞、代码组织和 token 数差异；已观察的六份独立代码输出均通过同一组执行测试。这意味着不能把所有逐字差异归因于 MTP，也不能宣称 greedy 严格确定。最终报告保留这一限制，不以少量代码测试替代完整质量 Benchmark。

## 最终部署与归档

- 选用 NInfer MTP=7、INT8 KV、prefill2048、64K、单会话；8K warm TTFT 中位数57ms，追加对话320ms。服务PID2675225、端口18081，身份/start ticks/实际命令行与HDD工作目录均核对；GPU0 PID2504785与18080健康。
- 默认输出8192、排队超时120秒；基准请求显式输出预算不变。未开启磁盘 prompt cache，前缀复用发生在内存状态。启动器固定HDD工作目录，所有环境缓存均指向HDD。
- 指标导出最初混合了同一提示的1024性能预算和2048质量预算；新增回归先观测1组而非2组，修正按源文件/预算分组后完整75项测试通过。
- 最终247次请求、155分组通过工件审计；4次历史协议失败保留，80次预算截断明确标注；30份独立代码与10份完整补测代码通过沙箱执行。
- NInfer原生请求日志按顺序与每次生成token数核对，提取草稿接收率。LRU三轮、三种draft配置的文本哈希完全相同；拓扑排序即使无MTP也变化，因此保留greedy非逐字确定的限制。
- 真实Anthropic工具调用及结果回传通过，耗时0.494秒；不宣称验证完整Claude Code客户端。
