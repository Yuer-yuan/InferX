# QoServe 适配：第一轮真实模型校准

当前完成了单张 RTX4090、现有27B模型、C4、MTP0、eager、FP8KV 的独立校准。
**第一轮预测器尚不合格，不能据此认定 QoServe 的调度机制解决不了混合负载问题。**
尚未进行 QoServe 正式混合负载比较，也没有使用正式结果拟合模型。

39组采样产生4493条真实模型完成步骤：25条初始吞吐采样、4129条训练步骤、339条独立留出步骤。
计时从原生调度入口到模型完成、原生输出更新结束；特征取实际 SchedulerOutput，包含实际输入起点、
预填充和解码 token 数及上下文。未以名义 chunk 代替执行量，未添加 CUDA 同步或自定义 worker。
原始数据、完整源代码快照和95个文件的逐文件哈希均已归档并在本机复核。

保留作者五特征 LinearRegression、80/20拆分与随机种子42、两分箱、1秒训练过滤和1.2倍预测保护。
本轮无需启用预先声明的5秒兼容过滤。训练中另有60条预热、212条作者规则排除的513-token步骤、
136条超过1秒的步骤；留出准确率使用全部非预热留出步骤，未按训练时间上限过滤。

需要区分三个校准问题：

1. 真实混合缓存块为1568token。无解码请求时，名义2048和2552两组各实际产生83步1568token和1步928token。
   这两组没有提供两种不同的大 chunk 执行形状。
2. 提出1792预算的留出步骤实际仅执行32token，或34个预填充token加2个解码token。
   128预算实际执行128个预填充token，或126个预填充token加2个解码token。这些都是真实执行量；
   不能把1792组解释为GPU处理1792token时预测失败。
3. 固定24K解码种子使解码数量与解码上下文高度相关。拟合得到很大的正负相抵系数；
   已观测步骤的预测均为正，但扩展到更长解码上下文的候选查询存在负预测。
   另有低分箱留出0–4K上下文被首5步预热剔除的覆盖缺口。

上述结果要求补充独立校准、再用新留出请求复验。当前不部署这些系数，不把校准失败计作 QoServe 的正式性能结果。
后续校准需覆盖实际的小执行形状、原方案会查询的总预算以及更分散的解码上下文；保留原调度策略与回归公式。

独立原生预算测量已启动，使用另7个新引擎运行24条串行短请求和3+3条冷长/续接长请求。
每组先做代码、4条24K严格工具请求和100条预置请求；只由这些独立测量冻结公共代理SLO。
实际HTTP QoS标签必须与引擎token时间逐请求对应。该阶段尚未完成，不报告预算或正式SLO达标率。
