问题与目标 · 02 / 08

单卡上同时满足质量、吞吐和延迟

正式负载

  • 8192 输入 / 512 输出；闭环并发 1、2、4、8。
  • 每档 100 正式请求，另行预热。
  • IFBench 前 100；保留四项原生分数。

成功标准

  • TTFT P95 ≤ 10 秒。
  • TPOT P95 ≤ 40 ms/token。
  • 质量可核验，环境可重建，原始记录完整。

ZIP 默认按 tiktoken 计 8192；参考文档按模型 tokenizer。正式口径需确认，不能混报。

本页按原版评测包组织；参考 MD 的并发/预热/超时差异见 PROTOCOL.md。

性能与取舍 · 07 / 08

长上下文容量与并发成绩，需要各自的证据

  • 24GB 卡上有限探针支持 253,914 输入；冷预填充约 200.8 秒，不适合现场等待，也不证明一般推理准确率。
  • 旧 Agent 配置为 256K、MTP7、单活动请求；四档闭环负载需要重新测并发与队列行为。
  • 更强短请求保护可能增加长请求耗时；同一张卡上的服务公平性有可测代价。
  • 48GB UCloud 可重新比较 FP8 与既有量化配置；用吞吐、联合 SLO 和质量决定方案。
资源成本：GPU 时间、显存、CPU/RAM、磁盘与部署耗时需填实测，不以客户端云 API 估价作为本地成本。
